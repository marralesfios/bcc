1. Notation

Pseudocode for a data types's consituents, as well as reference implementations for reading and writing each of the data types mentioned bellow will be given. Note that despite the struct keyword, the "declaration" is NOT meant to suggest any particular way of laying out or grouping your data. You might want to inline some of these types (such as muleb128) and make functions directly operate on their consituent(s), for example.

Notice that the serialization and deserialization functions in the example above simply recursively serialize/deserialize the contained data members sequentially in declaration order. In the following definitions, functions of this nature will be abbreviated with the keyword = sequential; in place of the function body.

In the write function, the last-written object can be changed through the special variable last. This is usually done after loops to eliminate branching, where it should be trivial to rewrite it as a condition inside the loop to test for the last iteration.

Generic types are denoted Type<T>, in which case T is the parameter.

Declaration, operators and control flow follow their obvious definitions, except that switch cases fall through if and only if the case is empty (alternatively: cases never fall through, but consecutive case labels are multiple conditions for entering the same case). Save for this exception, when in doubt, just follow C++'s semantics.

Uninitialized values are not used, and declared but not-yet-assigned-to variables are uninitialized. This means that in a language like Python, you might get away with not declaring them at all.

P.S. the data type is repeated in the signatures for read and write, so you can just do a text search if you want to go to the implementation of a specific type.

2. Fundamental Data Types

2.1 Basic integers

The types u8, u16, u32, u64, i8, i16, i32 and i64 are respectively unsigned and signed 8-, 16-, 32- and 64-bit integers. Reading and writing follow 2's complement (for signed numbers), little-endian format.

The types typeid and funcid are aliases of u32, but this might be changed later. Also see the note about serializing IDs.

2.2 Modified ULEB128

This is the "Modified unsigned LEB128" format. It is variable-length and has the same encoding for numbers of any width, so that is specified in a generic parameter. The unsigned number's binary representation is grouped into 7-bit septets in little-endian (i.e. most significant septet last) format (zero-padding the last septet if necessary, though this should go without saying), and an eighth (most-significant) bit, which is one if and only if it is the last septet in this number, is added to each septet, forming bytes, which are written. This high bit indicates the length of the number, as reading can stop after a byte that has its highest bit set is found.

Example: 257

Septet groups (BE)00000100000001
Septet groups (LE)00000010000010
Locationmiddleend
Bytes0000000110000010

Further reading (this is the "unmodified" version with only one difference: the high bits of all bytes are flipped in comparison to the encoding just described): https://en.wikipedia.org/wiki/LEB128#Unsigned_LEB128

2.3 String

A simple UTF-8 string. Note that memory allocation is elided: we assume that reading size automatically allocates chars correctly.

2.4 Color

An sRGB-space color.

3. Composite Data Types

3.1 Function Signature

A simple data structure representing a function's signature. Recall that functions always have exactly one argument.

3.2 Type pack

An array of type IDs. Works more or less the same as string.

3.4 Function

A function type.

3.5 Type info

Information about a type. Note that user-defined types are not supported yet, so there are no records for struct fields.

The type void here serves as a "default" union member. It is explicitly selected by "constructing" an object of type void via {} and assigning to that member. (Internally in the compiler, the union is actually a non-owning pointer, and this state is represented with a null pointer.)

3.6 Entity pool

A mapping from IDs to entries, where I is the index type and T is the element type. Here, Map is an associative array. It can be implemented with a hashmap. It is accessed with the [] indexing opearators, as found in many languages, and map.size() is the number of elements in the hashmap. We require it to fit inside the index type I, so we will assume that size() has a return type of I, even though you might need to insert a cast from u64 to u32 in practice.

A note on ID serialization

The types and functions must be serialized such that the entity with id N is the N+1-th entity that is serialized. In other words, the IDs must be sorted and contiguous starting from 0. In practice, because hashmap keys are not sorted and because editing may leave "holes" in the IDs, reassigning IDs when serializing is necessary. One way to do this is to directly iterate over the hashmap in arbitrary order, keeping a mapping from the original IDs to the iteration index, and serialize the iteration indices in place of IDs. The current compiler implementation uses this algorithm internally.
(This rule is subject to change.)

3.7 Project entity pool

This is the main data structure containing all data needed to compile a program.

3.8 Name

A data structure storing the user-friendly display name of an entity.

3.9 Name table

A table mapping function IDs to user-friendly display names.

3.10 Program

The master data structure, containing all information about a stored program. This is the data structured stored in a save file.
